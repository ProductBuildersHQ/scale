Why SCALE exists

Maturity frameworks make it cheap to generate hundreds of metrics, and cheap metrics destroy the story. Leadership cannot act on "maturity level 3 became level 4" repeated three hundred times. SCALE organizes every metric under one of five aspects — Standards, Consumption, Automation, Leverage, Effectiveness — so the platformization story can be told in five sentences, each backed by drill-down evidence. Domain dimensions (ordered lifecycles) provide each discipline's own story spine, orthogonal to the horizontal aspect view.

API Best Practices

Why API standardization matters

Every inconsistent API is a permanent tax: longer reviews, hand-written clients, breaking changes discovered by consumers. An executable style guide (api-style-spec) turns API design from tribal review knowledge into CI-enforced conformance, and conformant OpenAPI unlocks generated SDKs — leverage that compounds with every new service.

Q3: CI enforcement changed the conformance curve

Making style validation a blocking merge check (31% → 62% of repos) is what moved conformance, not enrollment: silver pass rate rose from 52% to 71% while enrollment grew more modestly. Teams fix what blocks their merge. Unplanned breaking changes fell from 7 to 4 — the first quarter the trend has pointed the right way.

Q4: close the enforcement gap, then SDK leverage (outlook)

Target is blocking validation at 80% of repos and silver pass rate at 85%. Once conformance is stable, the leverage story starts: generated SDKs from conformant OpenAPI should pass 60%.

Observability Best Practices

Why observability standardization matters

Installing a telemetry SDK is not observability. The journey is adoption (SDK installed), conformance (Golden Signals and RED/USE actually emitted with correct semantic conventions), and effectiveness (the signals are good enough that incidents are detected by alerts, not by customers). Standardized telemetry also creates leverage: shared dashboards and alert templates that every service inherits instead of rebuilding.

Instrumentation→Collection→Analysis→Alerting→Optimization

Q3: adoption is no longer the bottleneck — conformance is

OTel adoption reached 82%, but only 61% of instrumented services emit all four Golden Signals. The gap is concentrated in older Java services instrumented before the telemetry profile existed. MTTR improved from 132 to 98 minutes; alert-based detection rose to 67%, which we attribute to the RED dashboard rollout on the payment path.

Q4: auto-instrumentation closes the conformance gap (outlook)

Rolling auto-instrumentation to the legacy Java fleet should lift Golden Signals conformance past 80% without team-by-team migration work — the same enforcement-beats-enablement lesson the API domain learned this quarter. That is also the move that takes us from AWS Stage 2 toward Stage 3 practice.

Security Best Practices draft

The AI-era security story

Compliance frameworks like NIST CSF tell the auditor's story. This dimension tells the transformation story: security is shifting from human gatekeeping at a few chokepoints to AI-native practice at every lifecycle stage — AI threat modeling in design, defensive hygiene in development, automated posture in the pipeline, AI pentesting and red teams for offensive validation, and an AI-augmented SOC/CSIRT/PSIRT in operations. The maturity of each stage, read left to right, is the journey.
